# Consumer Signal Radar · 消费者洞察

## 变更定位

首次交付 v0.1：新增本地 Streamlit 最小 Demo；第 2 节列明能力边界，第 4 节说明数据格式，第 5 节说明大模型接入，第 7 节列明评测标准。此目录原本不存在，未修改同级简历文件。

## 1. 目标与运行

将一批评论转换为结构化反馈、话题排行和有原文证据的产品机会假设，演示 AI 产品经理从数据到验证决策的流程。

双击本目录的 **启动Demo.cmd**。电脑入口：<http://127.0.0.1:18521>。仅绑定本机，不是公网或手机预览；电脑和服务需保持运行。

当前已创建项目独立虚拟环境。换电脑时，在本目录执行：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m streamlit run app.py
```

## 2. 已实现与未验收

| 原要求 | 最小 Demo 实现 | 边界 |
|---|---|---|
| 800—1000 条公开评论 | 内置 1000 条**合成演示数据**，支持真实 CSV 替换 | 没有采集平台数据；12 类模板扩展，不能用于业务结论或模型验收 |
| 大模型结构化抽取 | 两种模式：离线规则；兼容接口大模型批量 JSON 抽取 | 离线不是 AI 语义理解；真实 API 需本机配置与实际请求验证 |
| Embedding + KMeans | 离线字符 TF-IDF + KMeans；在线真实 Embedding + KMeans | TF-IDF 是统计字符特征，不是语义模型；每条评论仅一个簇 |
| 热度、增长、机会分 | 样本热度、负面占比、严重度、等长窗口份额增长 | 未满足程度暂以负面占比代理；趋势只代表采样，不能证明市场趋势 |
| 产品痛点与新品机会 | 主题卡、研究假设、3—5 条原文、人工改名 | 少于 3 条不同负面原文不生成卡；不是已验证新品方案 |
| 可交互看板 | 品牌/产品/时间筛选、搜索、排行、趋势、CSV/报告下载 | 筛选保留原聚类，修改参数后需重新分析 |
| 100 条标注与 F1 ≥ 0.8 | 固定种子抽取 100 条空标签模板、上传标注计算四字段 Macro F1 | 尚无独立真实人工标注集，**未达到/未证明原定模型验收标准** |
| 案例、视频、说明 | 本说明、合成案例报告、操作演示 | 所有演示仅证明软件流程，不宣称品牌业务收益 |

不能把用户方案中的“珀莱雅真实痛点”“分析师 80% 时间”“节省 60%”及具体品牌事件当作已经验证的事实。本 Demo 不作这些声称。

## 3. 项目地图与行动路线

```text
CSV / 合成样本
  → 校验、去空、去完全重复、唯一编号
  → 离线规则 或 大模型 JSON 抽取
  → 字符向量 或 语义 Embedding → KMeans 聚类
  → 按品牌 / 产品 / 日期筛选
  → 样本排行、趋势、证据门槛
  → 机会假设与原文追溯 → 报告导出
```

完成标准：能本机打开；CSV 真正进入 Python 分析链；筛选改变统计；每张卡关联当前数据原文；缺失信息不编造；异常有提示；模型失败不偷偷切成离线结果。

路线：①建立独立目录与数据契约 → ②实现分析与证据链 → ③完成看板 → ④工程和浏览器验证 → ⑤用真实数据完成业务评测。第⑤步需要真实获准数据与独立人工标注，不能用工程测试替代。

## 4. CSV 输入与使用

最少一列 `text`；也识别中文列名“评论”或“评论内容”。推荐列如下：

| 字段 | 用途 |
|---|---|
| id | 唯一证据编号；缺列时自动生成，提供时不可空或重复 |
| text | 原始评论，必填；单条最多 4000 字 |
| brand / product | 品牌、产品；缺失为“未指明”，不从“某国货”猜测品牌 |
| date | 评论日期，建议 YYYY-MM-DD；无法解析的日期不参与趋势 |
| platform / source_url | 来源平台及可选原文链接；没有链接仍可在导入数据中追溯 |
| data_kind | 来源标记；内置样本为“合成演示数据” |

UTF-8 或 GB18030 CSV；最多 5000 行、10 MB。相同原文/品牌/产品/平台/日期去重。不同日期的重复文案仍可能代表刷评，Demo 尚无刷评识别。平台覆盖与上传文件合法性由数据持有人确认。不要导入无需分析的个人信息。

操作：上传 → 点“开始分析” → 选择品牌/产品/日期 → 查看并选择机会 → 核对证据 → 导出。更换文件/模式/簇数后旧结果不会冒充新结果。刷新或重启可能清除本次会话数据，请下载需保留的结果。

## 5. 本机模型配置

在线模式调用兼容 `POST /chat/completions`（JSON 对象响应）与 `POST /embeddings` 的 HTTPS 服务。配置只读取本机进程环境：

| 环境变量 | 内容 |
|---|---|
| RADAR_BASE_URL | 服务 API 根地址，通常以 `/v1` 结尾 |
| RADAR_API_KEY | 仅本机保存的凭据，不要发到聊天或写进仓库 |
| RADAR_MODEL | 当前服务支持 JSON 输出的文本模型名称 |
| RADAR_EMBEDDING_MODEL | 当前服务支持的向量模型名称 |

从已设置这些变量的终端运行启动命令。界面只检测变量是否存在，不显示密钥；勾选发送同意并点击分析才调用。每批抽取 12 条、每批向量化 64 条，超时 60 秒；失败明确报错，结果不保存；不自动重试以避免重复计费。1000 条约 84 次抽取 + 16 次向量请求，费用由所配置服务决定。本轮不读取其他项目的凭据。

抽取严格校验评论 ID、字段、枚举和严重度范围，提示词把评论当数据；仍需人工复核，不能把格式正确当内容正确。源码保留原文，不让模型改写证据。

## 6. 评分与证据

基础优先级 = 100 × 主题评论数/当前评论总数 × 负面或混合评论占比 × 负面原文平均严重度/3。

趋势机会分 = 基础优先级 × 增长倍数（限制 0—3）。增长倍数 = 最近 7 日主题份额 / 此前 7 日主题份额。主题份额用当天窗口内全部样本作分母，避免简单导入量增加被误判为主题增长。日期跨度不足 14 日、前期无样本或主题零基数时显示不可计算。未提供采样计划，所以即使有分数，也仅是样本信号。

至少 3 条不同负面原文才生成卡；选取严重度较高的最多 5 条，属于“问题证据”而非全体代表性样本。正向及混合观点在原始评论页保留。每条都带 ID、原文、产品、平台、日期、可选来源链接。没有负面证据不生成新品断言。

## 7. 测试与后续正式验收

```powershell
.\.venv\Scripts\python.exe -m unittest test_core -v
```

工程测试检查导入边界、否定句、唯一 ID、少样本、证据对应、日期窗口及标注错误。它们不等于模型 F1。

人工评测：下载空标签样本 → 独立标注 → 上传 → 查看 `feedback_type`、`dimension`、`sentiment`、`severity` 四字段的 Macro F1（先算每个类别的 F1，再平均）。完整目标还需对场景、成分、诉求设定实体/语义匹配规则；本轮只实现四字段，不声称关键字段全项已通过。正式验收应另准备至少 100 条真实且未用于调规则的评论、保留来源、复核分歧，并测试复杂否定、反讽、混合评价和无品牌反馈。
