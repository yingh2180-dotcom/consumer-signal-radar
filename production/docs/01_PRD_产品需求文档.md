# Consumer Signal Radar 产品需求文档

## 1. 变更定位

- 新增文件：production/docs/01_PRD_产品需求文档.md
- 文档作用：统一说明产品为什么做、为谁做、做什么、怎样验收。
- 当前口径：描述本机正式版已经实现的功能，同时明确真实数据、真实模型和公网部署仍未完成。

## 2. 产品概述

### 2.1 一句话定义

Consumer Signal Radar 是一个把分散、口语化的美妆用户评论转成可追溯产品机会的消费者洞察系统。

### 2.2 要解决的问题

1. 评论散落在多个平台，人工复制、整理和对比耗时。
2. 普通词频工具无法理解“上脸烫但不是过敏”等上下文。
3. 不直接出现品牌名的隐性讨论容易漏检。
4. 分析师把大量时间花在清洗和归类，洞察到达产品团队时已经滞后。

### 2.3 核心价值

系统把评论转成结构化字段，归并相似话题，计算机会排序，并让每张机会卡回溯到原始评论。产品经理看到的不只是“大家在说什么”，还包括“问题有多集中、为什么值得处理、证据在哪里、下一步怎样验证”。

## 3. 用户与使用场景

| 用户 | 主要任务 | 期望结果 |
|---|---|---|
| 消费者洞察分析师 | 导入、清洗、分析评论 | 少做重复整理，快速发现高频痛点 |
| 产品经理 | 查看机会卡和证据 | 获得可进入需求讨论的机会假设 |
| 研发或配方团队 | 查看成分、场景与严重度 | 定位需要复测的使用条件 |
| 品牌与舆情团队 | 查看负面趋势 | 尽早发现需要人工复核的风险信号 |
| 面试官或评审 | 体验完整闭环 | 理解候选人的产品、AI与工程能力 |

典型场景：分析师创建“双抗精华近三月反馈”项目，导入公开评论，运行分析，筛选“刺激泛红”，查看原文证据，保存报告并下载留档。

## 4. 产品目标与成功指标

### 4.1 当前版本目标

- 跑通登录、建项目、导入、分析、洞察、证据复核、报告保存和下载的完整闭环。
- 每条结构化结果包含产品、反馈类型、维度、场景、成分、情感和严重程度。
- 每张正式机会卡至少关联 3 条去重后的负面或混合原文证据。
- 明确区分合成演示数据、来源未核验数据和真实市场结论。
- 支持离线演示，未配置模型密钥时仍能稳定展示。

### 4.2 业务目标

- 将评论整理时间显著压缩，让分析师把时间用于解释和决策。
- 用统一证据链支持产品迭代和竞品对比。
- 对潜在负面信号提供更早的人工复核入口。

### 4.3 验收指标

| 指标 | 目标 | 当前状态 |
|---|---:|---|
| 核心流程可完成率 | 100% | 已通过本机浏览器验证 |
| 机会卡原文证据 | 每卡至少 3 条 | 已由规则和测试约束 |
| 无证据结论 | 0 | 已由生成规则约束 |
| 关键字段抽取 F1 | 不低于 0.80 | 尚未完成，缺 100 条人工金标与真实模型运行 |
| 后端自动化测试 | 全部通过 | 22 项已通过 |
| 前端生产构建 | 成功 | 已通过 |

F1 是准确率与召回率的综合分数。没有人工标注的标准答案，就不能诚实地宣称 F1 已达标。

## 5. 范围

### 5.1 当前版本已实现

- 本机账号登录与会话校验。
- 项目创建和项目列表。
- CSV、XLSX 评论导入及字段映射。
- 合成示例数据导入。
- 导入预检、错误行提示、内容指纹去重。
- 后台分析任务、进度查询、失败重试和断点恢复基础能力。
- 离线规则分析与可选真实模型分析。
- 主题聚合、趋势、严重度和机会分。
- 机会卡、证据抽屉、证据审核。
- 报告保存、查看和下载。
- 预算上限、模型调用账本和熔断。
- SQLite 备份、完整性检查与安全恢复。

### 5.2 当前不宣称完成

- 自动抓取抖音、小红书、天猫、京东。
- 对生产平台的持续实时监控。
- 已获得授权的 800 至 1000 条真实多平台数据。
- 真实模型抽取质量达到 F1 0.80。
- 企业级单点登录、复杂权限和多人协作。
- 公网高可用部署、告警和灾备演练。

## 6. 用户故事

- US-01：作为分析师，我想登录系统，以保护项目与报告。
- US-02：作为分析师，我想创建独立项目，以区分品牌、产品和分析周期。
- US-03：作为分析师，我想导入常见文件格式，以减少手工录入。
- US-04：作为分析师，我想在正式入库前看预检结果，以修正字段和错误行。
- US-05：作为分析师，我想启动后台分析并看到进度，以确认任务仍在工作。
- US-06：作为产品经理，我想按产品、平台和时间筛选，以聚焦目标人群或阶段。
- US-07：作为产品经理，我想查看机会排序和计算依据，以理解优先级。
- US-08：作为评审者，我想从机会卡打开原始评论，以核对结论。
- US-09：作为分析师，我想标记证据是否有效，以形成可审计的人工复核记录。
- US-10：作为用户，我想保存并下载报告，以便汇报和归档。

## 7. 功能需求

### 7.1 账号与项目

- FR-01：系统必须拒绝未登录用户访问业务接口。
- FR-02：登录失败时必须显示可理解的错误。
- FR-03：用户必须能创建项目并填写名称、描述和分析范围。
- FR-04：项目列表必须显示数据量、任务状态和更新时间。

### 7.2 数据导入

- FR-05：支持 CSV、XLSX。
- FR-06：预检必须显示识别字段、有效行、错误行和示例。
- FR-07：关键字段缺失时必须阻止提交并说明修复方法。
- FR-08：重复评论必须基于内容指纹去重并展示统计。
- FR-09：每批数据必须记录来源类型与来源核验状态。
- FR-10：合成数据必须在界面和报告中显式标记。

### 7.3 分析任务

- FR-11：分析必须以后台任务运行，页面刷新后仍可查询。
- FR-12：任务状态至少包含等待、运行、完成、失败和取消。
- FR-13：任务失败必须保存错误原因，并允许安全重试。
- FR-14：未配置真实模型时，用户可选择离线演示模式。
- FR-15：真实模型模式必须受单次和累计预算控制。

### 7.4 洞察与证据

- FR-16：系统必须生成结构化评论、主题聚合和机会排序。
- FR-17：机会分必须显示组成因素，避免把排序当作绝对真理。
- FR-18：每张机会卡必须展示样本事实、待验证假设、验证建议和结论边界。
- FR-19：正式机会卡至少包含 3 条去重的负面或混合原文证据。
- FR-20：证据必须显示原文、平台、日期、产品和审核状态。
- FR-21：用户必须能对证据执行通过、驳回或待定操作。
- FR-22：筛选条件必须作用于概览、趋势、机会和证据。

### 7.5 报告

- FR-23：用户必须能保存当前分析结果为报告。
- FR-24：报告必须记录样本量、去重数、来源状态、分析模式和限制。
- FR-25：报告必须能下载为便于面试展示和复核的文件。
- FR-26：报告不得把合成数据或未核验来源描述为真实市场事实。

## 8. 体验要求

- 新用户进入后能在 3 分钟内通过示例数据完成一次分析。
- 所有主要页面提供空状态、加载状态、成功状态和错误状态。
- 专业术语第一次出现时给出说明。
- 危险或付费动作在执行前显示清晰提示。
- 桌面端用于完整操作，390 像素宽手机页面不得横向溢出。
- 页面持续展示当前分析模式与数据可信度，避免演示时误读。

## 9. AI 行为与质量边界

- AB-01：模型只输出符合约定 Schema 的结构化结果；解析失败进入重试或人工处理。
- AB-02：证据不足时必须降级为待验证信号，不生成确定性建议。
- AB-03：无法识别的品牌、产品、成分或场景允许为空，不得编造。
- AB-04：离线模式用于流程演示，结论不得包装成真实语义模型洞察。
- AB-05：真实模型模式记录模型、请求批次、估算费用和失败原因，但不记录密钥。
- AB-06：质量验收使用独立的 100 条人工金标，关键字段 F1 不低于 0.80。

## 10. 异常与边界场景

| 场景 | 系统行为 |
|---|---|
| 空文件或错误格式 | 阻止导入，说明支持格式 |
| 字段名不一致 | 引导字段映射 |
| 同一评论重复导入 | 去重并返回重复数量 |
| 评论信息不足 | 保留原文，缺失字段为空 |
| 模型超时或返回坏 JSON | 有限重试，失败后保存原因 |
| 预算达到 20 元上限 | 停止新模型调用，保留已有结果 |
| Worker 中断 | 租约过期后可恢复或重试 |
| 没有足够有效证据 | 不生成正式机会卡 |
| 日期缺失 | 可参与总体统计，不进入时间趋势 |
| 下载失败 | 保留服务器端报告，允许再次下载 |

## 11. 技术与合规约束

- 仅导入公开、获授权或合成内容，不绕过平台反爬机制。
- API Key 只保存在本机环境变量中，不写进聊天、代码、数据库或报告。
- 当前本机正式版使用 React、Vite、FastAPI、SQLite 和独立 Worker。
- 正式模型默认关闭，只有本机配置密钥并显式选择后才会调用。
- 预算上限为用户已确认的 20 元；达到上限必须熔断。
- 业务数据恢复不能覆盖或回滚独立预算账本。

## 12. Agent 执行约定

### 权威来源

1. 实际运行的代码和自动化测试。
2. production/CONTRACT.md 中的接口与状态约定。
3. 本 PRD 的产品范围与验收标准。
4. 项目进度、数据评测和本机验收记录。

### 不可擅自改变

- 不得把合成数据改称真实数据。
- 不得绕过证据数量、来源标记和预算熔断。
- 不得修改或公开 .env、runtime 目录中的密钥或敏感数据。
- 不得在未经授权时部署到公网或产生模型费用。

### 验证要求

- 修改接口后运行后端全量测试。
- 修改前端后运行生产构建与关键浏览器流程。
- 修改数据或模型逻辑后复核机会卡证据与报告限制说明。
- 失败时记录具体步骤、日志位置和影响范围。

## 13. 依赖与风险

| 依赖或风险 | 影响 | 缓解方式 |
|---|---|---|
| 百炼 API Key 尚未配置 | 不能验收真实模型 | 保留离线模式；配置后执行小批量测试 |
| 缺少授权真实数据 | 不能证明市场洞察 | 使用合成数据演示流程，另行准备合规数据 |
| 缺少人工金标 | 不能计算可信 F1 | 按 DATA_EVALUATION.md 标注 100 条 |
| SQLite 并发能力有限 | 不适合大规模多人生产 | 面试版保留；规模扩大时迁移 PostgreSQL |
| Docker 当前未验证 | 容器部署存在未知项 | 本机原生版作为已验证基线，安装环境后再验 |
| 机会分权重具有业务假设 | 排序可能偏离团队判断 | 展示分项、允许复核并用历史结果校准 |

## 14. 里程碑

1. M1 本机闭环：代码、测试、生产构建和浏览器流程完成。
2. M2 文档交付：PRD、架构、操作、工作流、ADR、验收和面试手册完成。
3. M3 真实模型：配置本机密钥，在 20 元预算内进行小样本联调。
4. M4 数据评测：准备 100 条人工金标并计算各字段 F1。
5. M5 部署验证：验证 Docker 或选定云平台，完成上线检查。
