# Consumer Signal Radar 业务与系统工作流

## 1. 变更定位

- 新增文件：production/docs/04_业务与系统工作流.md
- 文档作用：说明人怎样使用系统、系统内部怎样处理数据，以及每一步由谁负责。

## 2. 端到端业务流程

~~~mermaid
flowchart TD
    A[明确研究问题] --> B[准备公开或获授权评论]
    B --> C[导入预检与去重]
    C --> D[确认入库]
    D --> E[结构化抽取]
    E --> F[主题归并与指标计算]
    F --> G[生成证据约束的机会卡]
    G --> H[分析师复核原文]
    H --> I[保存报告]
    I --> J[产品团队验证假设]
    J --> K[产品或传播决策]
~~~

系统做到报告和验证建议为止。产品立项、配方变更或舆情处置仍由业务负责人决策。

## 3. 五个阶段

| 阶段 | 人的动作 | 系统动作 | 输出 | 质量闸门 |
|---|---|---|---|---|
| 定义问题 | 明确产品、时间、平台 | 创建项目 | 研究范围 | 范围不可含糊 |
| 准备数据 | 确认来源和授权 | 预检、映射、去重 | 可分析评论 | 错误行已处理 |
| 自动分析 | 选择模式并提交 | 抽取、归并、计算 | 主题和指标 | 失败可追踪 |
| 人工复核 | 阅读并审核证据 | 保存审核状态 | 可信机会卡 | 每卡至少 3 条证据 |
| 决策验证 | 选择下一步实验 | 生成和下载报告 | 验证计划 | 不把相关性当因果 |

## 4. 数据生命周期

~~~mermaid
stateDiagram-v2
    [*] --> 待预检
    待预检 --> 被拒绝: 格式或字段错误
    待预检 --> 已入库: 用户确认
    已入库 --> 待分析: 创建任务
    待分析 --> 分析中: Worker领取
    分析中 --> 分析失败: 异常
    分析失败 --> 待分析: 安全重试
    分析中 --> 已完成: 结果写入
    已完成 --> 待复核: 生成洞察
    待复核 --> 已复核: 人工审核
    已复核 --> 已归档: 保存报告
~~~

原始评论始终保留，结构化字段和主题是分析产物。重新分析应创建新的运行记录，不能静默覆盖旧结果。

## 5. 后台任务工作流

1. API 创建等待任务并返回任务编号。
2. Worker 领取任务，写入租约和心跳。
3. Worker 分批读取评论并调用分析引擎。
4. 每批完成后写入检查点和进度。
5. 完成后保存结构化结果、主题、指标和机会卡。
6. 失败时保存错误原因；符合条件的任务可重试。
7. 前端按任务编号查询状态并展示。

这让页面刷新后仍能继续查看任务。

## 6. 真实模型工作流

~~~mermaid
flowchart TD
    A[选择真实模型] --> B{付费开关开启?}
    B -- 否 --> X[拒绝调用]
    B -- 是 --> C{Key配置完整?}
    C -- 否 --> X
    C -- 是 --> D{预算充足?}
    D -- 否 --> Y[熔断并提示]
    D -- 是 --> E[分批发送必要文本]
    E --> F[校验结构化JSON]
    F -->|失败| G[有限重试或记录失败]
    F -->|成功| H[记录用量与估算费用]
    H --> I[进入证据与统计规则]
~~~

模型只辅助理解文本。系统仍需校验 Schema、证据数量、来源状态和结论边界。

## 7. 证据审核工作流

审核者依次检查：

1. 原文是否表达该主题；
2. 产品、平台和日期是否一致；
3. 是否与其他证据重复；
4. 情感和严重程度是否合理；
5. 原文能支持“样本事实”到什么程度。

通过表示支持当前归类；驳回表示不支持；待定表示需要更多上下文。审核状态不等于来源授权状态。

## 8. 评测工作流

~~~mermaid
flowchart LR
    A[抽取至少100条样本] --> B[制定标注规范]
    B --> C[人工独立标注]
    C --> D[解决分歧形成金标]
    D --> E[运行真实模型]
    E --> F[逐字段比对]
    F --> G[计算Precision Recall F1]
    G --> H{关键字段F1至少0.80?}
    H -- 否 --> I[分析错误并改进]
    I --> E
    H -- 是 --> J[记录版本和通过证据]
~~~

测试集不能一边调提示词一边作为最终成绩，否则会产生针对题目的偏差。

## 9. 角色分工

| 工作 | 数据负责人 | 分析师 | 产品经理 | 系统 |
|---|---|---|---|---|
| 确认来源授权 | 主责 | 协助 | 知情 | 记录状态 |
| 定义研究范围 | 协助 | 主责 | 主责 | 保存项目 |
| 修正导入错误 | 主责 | 主责 | 知情 | 预检提示 |
| 运行分析 | 知情 | 主责 | 知情 | 自动执行 |
| 审核证据 | 协助 | 主责 | 复核 | 保存记录 |
| 决定产品行动 | 知情 | 建议 | 主责 | 不代替决策 |
| 备份和恢复 | 运维主责 | 知情 | 知情 | 校验完整性 |

## 10. 面试演示工作流

1. 说明业务痛点和目标。
2. 声明使用合成数据和离线模式。
3. 用 5 至 8 分钟完成登录到报告的流程。
4. 打开一张机会卡，展示事实、假设、建议、边界和原文。
5. 解释 Worker、证据约束、预算熔断和 F1 设计。
6. 主动说明真实模型、真实数据、Docker 和公网仍待验收。

## 11. 完成标准

- 每批数据能说明来源类型和核验状态。
- 每次分析有独立任务记录和明确状态。
- 每张正式机会卡至少 3 条原文证据。
- 报告可追溯项目、批次、分析模式和限制。
- 真实模型调用有预算记录和熔断。
- 真实质量结论来自独立人工金标评测。
