# Consumer Signal Radar 技术架构说明

## 1. 变更定位

- 新增文件：production/docs/02_技术架构说明.md
- 文档作用：用小白能理解的方式说明系统由什么组成、数据怎样流动、失败后怎样恢复。
- 阅读前提：不要求具备编程经验。

## 2. 先用一个比喻理解

可以把系统想成一家餐厅：

- React 前端是服务员，接收用户操作并展示结果。
- FastAPI 后端是前台经理，检查身份、校验数据、安排任务。
- SQLite 是账本，保存项目、评论、任务、洞察和报告。
- Worker 是后厨，专门执行耗时的分析任务。
- 分析引擎是厨师，可选择离线规则配方或真实大模型配方。
- 预算账本是收银系统，限制真实模型费用。

前端不会直接修改数据库，也不会把密钥交给浏览器。所有业务操作先进入后端。

## 4. 组件职责

| 组件 | 作用 | 关键位置 |
|---|---|---|
| 前端 | 登录、项目、导入、任务进度、洞察、证据和报告界面 | production/frontend |
| API 服务 | 身份校验、参数验证、读写业务数据、提供下载 | production/backend/server.py |
| 分析引擎 | 结构化抽取、主题归并、指标与机会卡生成 | production/backend/engine.py |
| Worker | 领取任务、续租、执行、重试、写回结果 | production/backend/worker.py |
| 数据层 | 表结构、事务、迁移和数据库连接 | production/backend/db.py |
| 启动器 | 启动 API 与 Worker，检查运行状态 | production/launch.py |
| 维护工具 | 备份、校验和恢复 | production/maintenance.py |
| 前后端契约 | 统一字段、状态、错误与版本边界 | production/CONTRACT.md |

## 5. 一次分析怎样完成

~~~mermaid
sequenceDiagram
    actor User as 用户
    participant UI as 前端
    participant API as FastAPI
    participant DB as SQLite
    participant Worker as Worker
    participant Engine as 分析引擎

    User->>UI: 登录并创建项目
    UI->>API: 提交评论文件预检
    API-->>UI: 返回字段、有效行和错误行
    User->>UI: 确认导入
    UI->>API: 写入评论
    API->>DB: 去重并保存批次
    User->>UI: 启动分析
    API->>DB: 创建等待任务
    Worker->>DB: 领取任务并建立租约
    Worker->>Engine: 分批分析评论
    Engine-->>Worker: 结构化结果、主题和机会卡
    Worker->>DB: 保存检查点和最终结果
    UI->>API: 轮询任务进度
    API-->>UI: 返回状态与洞察
    User->>UI: 查看并审核原文证据
    UI->>API: 保存或下载报告
~~~

租约可以理解为“这张任务单暂时由某个 Worker 负责”。如果 Worker 意外退出，租约过期后任务可被重新领取，避免永远卡在运行中。

## 6. 数据模型

数据库以项目为主线，主要实体关系如下：

~~~mermaid
erDiagram
    USER ||--o{ SESSION : owns
    USER ||--o{ PROJECT : creates
    PROJECT ||--o{ IMPORT_BATCH : contains
    IMPORT_BATCH ||--o{ REVIEW : imports
    PROJECT ||--o{ ANALYSIS_RUN : runs
    ANALYSIS_RUN ||--o{ STRUCTURED_REVIEW : produces
    ANALYSIS_RUN ||--o{ TOPIC : groups
    TOPIC ||--o{ EVIDENCE : supports
    PROJECT ||--o{ REPORT : saves
~~~

理解这些表时抓住三条线：

1. 来源线：导入批次指向原始评论，回答“数据从哪里来”。
2. 分析线：分析任务指向结构化结果和主题，回答“机器做了什么”。
3. 证据线：机会卡指向原文证据，回答“结论凭什么成立”。

预算记录保存在独立数据库中。恢复业务备份时不会回滚已经产生的累计费用。

## 7. API 分层

接口按用途分为：

- 认证：登录、退出、当前会话。
- 项目：创建、列表、详情。
- 导入：上传预检、确认入库、示例数据。
- 分析：创建任务、查询状态、取消或重试。
- 洞察：概览、趋势、主题、机会卡和证据。
- 审核：修改证据审核状态。
- 报告：保存、查看、下载。
- 运维：健康检查、就绪检查和运行信息。

具体路径和请求响应结构以 production/CONTRACT.md 为准。契约文件相当于前端和后端共同遵守的“对接说明”。

## 8. 两种分析模式

### 8.1 离线演示模式

不访问外部模型，根据词典、规则和已实现的主题逻辑完成流程。优点是免费、稳定、适合面试；局限是语义理解和泛化能力有限。输出必须标记为演示或探索性结果。

### 8.2 真实模型模式

通过兼容接口调用已配置的模型服务，用结构化提示词抽取字段。模型调用受预算、批次、超时、重试和 JSON 校验约束。模型并不直接给最终商业结论，后端仍负责证据约束、统计和报告边界。

### 8.3 为什么保留两种模式

面试现场首先需要稳定展示完整产品链路；真实模型则用于证明语义抽取能力。两者共用数据结构和界面，因此切换模式不会推倒整个系统。

## 9. 主题与机会分

系统先把相似反馈归到主题，再计算热度、增长、严重度和未满足程度。机会分用于排序，不等于市场真相。

示意公式：

机会分 = 热度因子 × 增长因子 × 严重度因子 × 未满足因子

为避免小样本产生夸张结果，系统还要求：

- 展示样本数和来源状态。
- 机会卡至少有 3 条去重的负面或混合证据。
- 区分样本事实、待验证假设、验证建议和结论边界。
- 无法满足证据条件时不生成正式机会卡。

## 10. 任务可靠性

- 状态机：等待、运行、完成、失败、取消。
- 心跳：Worker 定期表明自己仍存活。
- 租约：防止多个 Worker 同时执行同一任务。
- 检查点：分批保存进度，意外中断后减少重复工作。
- 幂等：重复提交相同评论时通过指纹去重。
- 有限重试：只对适合重试的错误重试，最终失败会保存原因。

幂等的意思是“同一操作重复执行，最终不会多出重复结果”。

## 11. 安全、隐私与费用

- 密码以摘要形式保存，会话由后端校验。
- API Key 可通过登录后的本机配置页单向提交，由服务端原子写入 `.env`；后续只从服务端环境变量读取，任何查询响应都不返回密钥。
- 数据库、备份、运行日志和导出目录不应公开。
- 仅处理公开、获授权或合成数据。
- 真实模型默认关闭，累计费用达到 20 元时停止新调用。
- 预算账本与业务备份隔离，避免通过恢复旧数据规避上限。
- 日志不打印密钥和完整敏感载荷。

## 12. 启动与部署结构

### 12.1 已验证的本机路径

1. 构建前端静态文件。
2. 启动器拉起 FastAPI 和 Worker。
3. FastAPI 同时提供 API 与前端静态资源。
4. 浏览器访问本机地址。

### 12.2 容器路径

项目提供 Dockerfile 与 compose.yaml，用于把运行环境一起打包。当前尚未完成真实 Docker 引擎下的构建、启动、持久化和恢复验收，因此只能称为“部署配置已准备”。

### 12.3 上线前还要补什么

- 使用真实域名和 HTTPS。
- 替换演示密码并启用安全密钥管理。
- 确认数据库持久化目录和备份策略。
- 增加反向代理、请求大小限制和访问日志。
- 验证容器健康检查、重启策略和回滚。
- 根据并发量决定是否把 SQLite 迁移到 PostgreSQL。

## 13. 故障定位顺序

1. 页面打不开：检查 API 进程、端口和健康接口。
2. 能登录但任务不动：检查 Worker 心跳和任务租约。
3. 导入失败：看预检返回的字段和错误行。
4. 真实模型失败：检查是否启用、密钥是否只在本机配置、预算是否已达上限。
5. 报告缺少机会卡：检查有效负面证据是否达到 3 条。
6. 恢复失败：检查备份完整性、目标目录是否为空、备份是否错误包含预算账本。

已验证：前端生产构建、22 项后端自动化测试、本机完整浏览器流程、390 像素移动端无横向溢出。

### 账号与数据隔离架构

`users` 保存规范化用户名、显示名、带盐 scrypt 密码哈希、角色和状态；`sessions` 将不可预测的会话令牌关联到用户或管理员身份。请求中间件只从 HttpOnly Cookie 解析身份，业务接口不接受前端提交的所有者编号作为授权依据。

`projects.owner_type` 区分 `system` 与 `user`，`owner_user_id` 指向私人项目所有者，`source_project_id` 记录公共样本复制来源。评论、批次、任务、洞察、评测和报告通过项目归属统一校验；无权访问的对象返回 404。旧演示项目在幂等迁移中转为系统样本，原有业务记录保持不变。
