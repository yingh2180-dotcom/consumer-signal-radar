# 数据归属路由审计

## 变更定位

- 改动标题：项目及下游数据接口的所有权审计。
- 所在模块：`backend/server.py`、`backend/db.py`。
- 操作类型：只读审计；本文件不修改运行代码或数据库。
- 审计对象：项目、评论/导入批次、分析任务、洞察卡、报告、评测、导出和备份。

## 1. 结论

当前认证中间件只确认“存在一个未过期的会话”，没有把用户身份放入请求，也没有按项目过滤数据（`server.py:44-58`）。数据库中的 `sessions` 只有 `token`、`expires`，`projects` 也没有所有者字段（`db.py:36-43`）。因此，现有代码适合单管理员模式；一旦开放多用户，所有下列接口都会成为跨用户读取、修改或导出的入口。

应把授权集中到两个解析器，而不是在每条路由手写 SQL：

1. `require_read_project(request, c, pid)`：仅允许系统样本或当前用户拥有的项目读取。
2. `require_write_project(request, c, pid)`：仅允许当前用户拥有的私人项目写入；系统样本始终拒绝写入。需要使用样本时，先复制为当前用户的私人项目。

独立 ID 路由先按 `job_id` 或 `report_id` 取其 `project_id`，再调用上述解析器；不能把“对象存在”当成“当前用户有权”。对已登录但无权的对象统一返回 404，避免通过 UUID 探测资源。

## 2. 归属链与校验原则

```text
当前会话身份
  └─ 项目（owner_type / owner_user_id）
       ├─ 导入预览、导入批次、评论
       ├─ 分析任务
       │    └─ 结果中的洞察卡、评测输入/结果、CSV 导出
       └─ 报告
            └─ Markdown 下载
```

现有表已保存项目到下游对象的关联：`previews.project_id`、`batches.project_id`、`reviews.project_id`、`jobs.project_id`、`reports.project_id`（`db.py:38-43`）。迁移后不需要给每张下游表重复写用户编号；但是每个以独立下游 ID 查询的接口必须沿着该关联回查项目所有权。

| 操作 | 授权规则 |
| --- | --- |
| 读取 | `owner_type='system'` 或 `owner_user_id == current_user.id` |
| 写入、触发分析、评测、生成报告 | `owner_type='user'` 且 `owner_user_id == current_user.id` |
| 系统样本 | 可列出/读取；不能直接导入、修改洞察、发起任务、创建报告或评测，应先复制到私人项目 |
| 管理员 | 仅管理模型配置；不因管理员角色自动读取其他用户私人项目 |

## 3. 路由清单与所需校验

| 资源与路由 | 当前关联方式 | 需要的权限 | 当前缺口/风险 |
| --- | --- | --- | --- |
| `GET /api/projects`（`server.py:197-199`） | 无过滤地查询所有项目 | 只返回系统项目和当前用户项目 | **高**：多用户下直接泄露所有项目名称、描述和编号。 |
| `POST /api/projects`（201-206） | 新项目无 owner 字段 | 当前登录用户；创建时写入 `owner_type='user'`、`owner_user_id` | **高**：会生成无主项目，后续无法判定归属。 |
| `POST /api/projects/{pid}/imports/preview`（245-254） | `pid -> projects`；创建 `preview_id` | 项目写权限 | **高**：可向他人项目写入预览和上传内容。预览记录通过项目继承归属。 |
| `POST /api/projects/{pid}/imports`（287-294） | `preview_id + pid -> previews`，随后写入批次/评论 | 项目写权限；预览必须属于该项目 | **高**：只比对 preview 与项目，不比对当前用户；项目授权必须在读取预览前完成。 |
| `GET /api/projects/{pid}/imports`（296-301） | `pid -> batches` | 项目读权限 | **高**：泄露批次名、来源类型、数量和质量数据。 |
| `POST /api/projects/{pid}/demo`（303-308） | `pid -> projects`，写入批次/评论 | 项目写权限 | **高**：可污染他人项目；系统样本也不能直接写。 |
| `GET /api/projects/{pid}/reviews`（310-319） | `pid -> reviews`，可带 `batch_id` | 项目读权限；若提供 `batch_id`，确认其属于该项目 | **高**：评论正文和来源编号会泄露。现有 SQL 用 `project_id` 限制结果，但未先判定访问项目的身份。 |
| `POST /api/projects/{pid}/jobs`（327-343） | `pid -> batches/reviews -> job` | 项目写权限；每个 `batch_id` 必须属于该项目 | **高**：可用他人项目评论启动任务，消耗模型额度并产生派生数据。现有批次归属检查可保留，但不能取代项目所有权校验。 |
| `GET /api/projects/{pid}/jobs`（350-353） | `pid -> jobs` | 项目读权限 | **高**：泄露任务状态、错误、时间和任务编号。 |
| `GET /api/projects/{pid}/reports`（448-451） | `pid -> reports` | 项目读权限 | **高**：泄露报告题目、时间和后续可用于直接下载的编号。 |
| `GET /api/jobs/{jid}`（355-357） | `jid -> jobs.project_id` | 先解析任务所属项目，再做项目读权限 | **严重的间接 ID 越权**：`get_job` 只按任务 UUID 查询。 |
| `POST /api/jobs/{jid}/cancel`（359-365） | `jid -> jobs.project_id` | 先解析任务，再做项目写权限 | **严重的间接 ID 越权**：可取消他人排队/运行任务。 |
| `POST /api/jobs/{jid}/retry`（367-374） | `jid -> jobs.project_id` | 先解析任务，再做项目写权限 | **严重的间接 ID 越权**：可重试他人任务，可能触发付费模型。 |
| `GET /api/jobs/{jid}/result`（381-383） | `jid -> jobs.project_id -> result` | 先解析任务，再做项目读权限 | **严重的间接 ID 越权**：完整结果含评论、证据、洞察和趋势。 |
| `PATCH /api/jobs/{jid}/cards/{cid}`（389-403） | `jid -> job result -> embedded card` | 先解析任务，再做项目写权限；`cid` 只在该已授权任务结果中匹配 | **严重的间接 ID 越权**：可修改他人洞察假设和复核状态。洞察卡没有独立表，归属必须继承任务。 |
| `POST /api/jobs/{jid}/reports`（409-446） | `jid -> jobs.project_id`，新报告写入同项目 | 先解析任务，再做项目写权限 | **严重的间接 ID 越权**：可从他人结果创建包含原始证据的报告。 |
| `GET /api/reports/{rid}`（453-457） | `rid -> reports.project_id` | 先解析报告所属项目，再做项目读权限 | **严重的间接 ID 越权**：`report()` 只按报告 UUID 查询并返回完整快照。 |
| `GET /api/reports/{rid}/download`（459-461） | 复用 `report(rid)` | 同上，项目读权限 | **严重的间接 ID 越权**：下载继承 `report()` 的未授权读取问题。 |
| `GET /api/jobs/{jid}/export.csv`（470-472） | 复用 `result(jid)` | 先解析任务，再做项目读权限 | **严重的间接 ID 越权**：可批量导出他人评论。 |
| `GET /api/jobs/{jid}/annotation.csv`（474-487） | 复用 `result(jid)` | 先解析任务，再做项目读权限 | **严重的间接 ID 越权**：抽样文件仍含评论正文。 |
| `POST /api/jobs/{jid}/evaluate`（489-496） | 复用 `result(jid)`；上传评测集不持久化 | 先解析任务，再做项目写权限 | **高**：可用他人结果进行评测并读取返回指标；若以后保存评测结果，须以任务所属项目作为归属。 |

## 4. 最容易漏掉的间接 ID 查询

以下辅助函数是改造时的关键检查点。它们目前只验证“存在”，没有验证“谁在访问”：

1. `project(c, pid)`（`server.py:188-191`）是所有嵌套项目路由的入口。应替换为带 `Request`/身份参数的读写项目解析器；只改项目列表没有效果。
2. `get_job(c, jid)`（345-348）被任务详情、取消、重试和 `result_for` 共用。应改为返回“已授权任务”，或者新增 `require_read_job`、`require_write_job`，以免任一新路由绕过检查。
3. `result_for(c, jid)`（376-379）会被结果、洞察编辑、报告、两类 CSV 和评测复用。这里若只检查任务状态，所有继承它的接口都会暴露任务数据。
4. `report(rid)`（453-457）被报告详情和下载复用。下载不能因为调用内部函数而跳过项目读权限。
5. 请求体中的 `preview_id`（287-294）和 `batch_ids`（327-336）不是 URL 参数，却同样是外部可控 ID；必须在已授权项目范围内查询，不能先按全局 ID 查询后再“相信”结果。
6. 洞察 `cid` 是任务结果 JSON 内的 ID（389-403），没有数据库外键。只有先成功授权 `jid`，再在该任务结果内查 `cid`，才不会越权。

## 5. 备份与配置边界

`server.py` 与 `db.py` 中没有备份 HTTP 路由。备份/恢复只由本机命令行脚本 `maintenance.py` 执行，且要求目标目录原本不存在，因此不存在可经 API 利用的项目 ID 越权路径。

多用户上线后，原始 SQLite 备份包含所有用户数据，不能暴露为普通用户接口或由用户自行下载。备份、恢复、数据库路径和模型配置应保持本机运维/管理员专用；恢复只允许到隔离新目录，不能覆盖在线数据库。若未来增加备份 API，必须是管理员专用、服务器固定存储位置、带审计记录，且不得接受任意来源/目标路径。

与项目归属不同，`GET/POST /api/settings`（105-185）应按角色控制：普通用户只能获取脱敏可用状态，只有管理员可查看或修改服务地址、密钥和计费开关。

## 6. 实施验收建议

至少建立两名普通用户和一个管理员的测试矩阵：

- 两名用户均可读取系统样本；对系统样本的写入、任务、洞察编辑、报告和评测均被拒绝，复制后才允许操作私人副本。
- 用户 A 创建项目、导入评论、完成任务并生成报告后，用户 B 对本审计表每一个 `pid`、`jid`、`rid`、`preview_id`、`batch_id` 和 `cid` 入口访问时均得到 404，且无数据、任务状态或下载内容泄露。
- 用户 A 对自己的读取、写入、导出与评测流程仍正常；管理员可改设置，但不能通过项目、任务或报告 UUID 读取用户 A 的私人数据。
- 直接调用备份/恢复接口不存在；若保留命令行工具，验证其只能恢复到新目录，并且备份内容不经 Web 返回。
