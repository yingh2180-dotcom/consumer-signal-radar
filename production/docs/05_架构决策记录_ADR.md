# Consumer Signal Radar 架构决策记录

## 1. 变更定位

- 新增文件：production/docs/05_架构决策记录_ADR.md
- 文档作用：记录关键技术选择、理由、代价和未来何时重新评估。
- ADR 是 Architecture Decision Record 的缩写，即“架构决策记录”。

## 2. 阅读方法

每条 ADR 都回答四件事：当时遇到什么问题、最终选了什么、放弃了什么、这个选择带来什么后果。状态为“已接受”表示当前系统按该方案实现，不代表以后永远不能改变。

## ADR-001：采用 React 前端与 FastAPI 后端的同源应用

- 状态：已接受
- 日期：2026-09-08
- 决策者：项目开发者

### 背景

项目需要完整交互看板、文件上传、后台任务、报告下载和清晰的前后端边界。面试演示还要求一次启动后即可访问，减少跨域和多地址配置。

### 决策

使用 React 与 Vite 构建前端，FastAPI 提供业务 API，并在生产构建后由同一服务提供静态页面。浏览器统一通过同源的 /api 路径访问后端。

### 结果

正面影响：

- React 适合构建筛选器、图表、抽屉和多状态页面。
- FastAPI 的类型校验和自动接口能力适合快速开发数据产品。
- 同源部署减少跨域配置，面试现场启动更简单。

负面影响：

- 需要维护 JavaScript 与 Python 两套依赖。
- 前后端契约变化时必须同步修改并测试。

中性影响：

- 开发时前端可使用独立 Vite 服务，正式构建后由后端统一托管。

### 备选方案

- Streamlit：开发更快，但复杂交互、状态管理和正式产品感较弱。
- 单体服务端模板：依赖更少，但后续看板交互扩展不够灵活。
- 前后端分别部署：扩展性更好，但当前面试项目运维复杂度不划算。

### 重新评估条件

当团队只有 Python 开发者、页面交互显著收缩，或需要前后端独立扩容时重新评估。

## ADR-002：使用 SQLite 业务库与独立 Worker

- 状态：已接受
- 日期：2026-09-08
- 决策者：项目开发者

### 背景

分析任务可能持续数秒到数分钟。若直接在网页请求中执行，页面容易超时；若一开始引入 PostgreSQL、Redis 和专业任务队列，会增加面试部署成本。

### 决策

业务数据使用 SQLite；耗时任务由独立 Worker 领取。任务表记录状态、租约、心跳、检查点、重试信息和最终结果。

### 结果

正面影响：

- 无需额外数据库服务，本机可快速启动。
- API 与耗时分析隔离，页面可持续查询进度。
- 租约和检查点让中断恢复具备基础保障。

负面影响：

- SQLite 写并发有限，不适合高并发、多实例生产环境。
- 数据库任务队列不具备 Redis 或专业队列的全部调度能力。

中性影响：

- 当前数据量和单机面试场景下，该选择更容易复现和审查。

### 备选方案

- 请求内同步分析：最简单，但超时和恢复体验差。
- Celery 加 Redis：成熟，但组件和运维成本更高。
- PostgreSQL 队列：并发更强，但本机安装和部署步骤增加。

### 重新评估条件

出现多人同时分析、单日大量任务、多实例部署或明显锁等待时，迁移到 PostgreSQL 与专业任务队列。

## ADR-003：保留离线演示与真实模型双模式

- 状态：已接受
- 日期：2026-09-08
- 决策者：项目开发者与用户

### 背景

面试需要稳定、可重复、无网络也能运行；产品目标又需要展示大模型对口语化评论的结构化理解。真实模型还涉及密钥、费用、网络和输出波动。

### 决策

分析引擎提供两条路径：

1. 离线演示模式，以规则和本地算法跑通完整流程。
2. 真实模型模式，通过服务端配置的兼容 API 完成结构化抽取。

两种模式共用 Schema、任务系统、证据约束和看板。真实模型默认关闭，累计联调预算上限为 20 元。

### 结果

正面影响：

- 面试现场不依赖外网和余额。
- 可以在准备好密钥后逐步验证真实语义能力。
- 预算熔断降低误调用风险。

负面影响：

- 离线结果容易被误解为真实 AI 洞察，必须持续标识。
- 两条路径都要维护测试，结果可能存在差异。
- 更换模型时仍需重新评测提示词、Schema 和质量。

中性影响：

- 模型供应商只是能力依赖，证据、统计和业务限制仍由本系统控制。

### 模型选择原则

- 先用价格较低且结构化输出稳定的通用模型做 20 至 50 条小样本联调。
- 只有在字段 F1 或复杂语义明显不足时，才升级更强模型。
- 联调前按当日官方价格确认输入、输出和缓存计费，不能依赖旧价格记忆。
- API Key 仅在本机环境变量配置，不进入聊天或仓库。

### 备选方案

- 只用离线规则：稳定便宜，但不能证明大模型抽取价值。
- 只用真实模型：实现更单一，但现场稳定性、费用与可复现性较差。
- 本地开源模型：可控，但硬件、部署与中文效果验证成本更高。

### 重新评估条件

当真实模型完成 100 条金标评测、费用稳定且网络环境可靠后，可将其设为默认；若合规要求禁止外发文本，则评估本地模型。

## ADR-004：机会卡必须由原文证据约束

- 状态：已接受
- 日期：2026-09-08
- 决策者：项目开发者

### 背景

生成式模型容易给出听起来合理但没有数据支撑的建议。消费者洞察如果无法回到原文，产品经理无法判断结论是否来自真实样本。

### 决策

每张正式机会卡至少关联 3 条去重后的负面或混合原文，并分开呈现：

- 样本事实；
- 待验证假设；
- 验证建议；
- 结论边界。

证据不足时不生成正式机会卡。证据还要保留平台、日期、产品和人工审核状态。

### 结果

正面影响：

- 每个结论可复核，减少无依据建议。
- 面试中能清楚展示从数据到决策的链路。
- 人工审核结果可用于后续质量改进。

负面影响：

- 小样本主题可能没有卡片，页面结果数量较少。
- 证据去重和审核增加实现复杂度。

中性影响：

- 机会卡仍是决策输入，不能代替研发测试、市场调研或因果验证。

### 备选方案

- 允许模型自由生成建议：展示丰富，但可信度低。
- 每卡只给一条证据：容易被极端评论误导。
- 只展示统计图：可靠但难以转成具体行动。

### 重新评估条件

未来若引入更严格的统计显著性、用户分层和来源信誉评分，可提高证据门槛，但不能取消可追溯原则。

## ADR-005：本机原生版作为当前已验证部署基线

- 状态：已接受
- 日期：2026-09-08
- 决策者：项目开发者

### 背景

仓库已提供 Dockerfile 和 compose.yaml，但当前环境没有完成 Docker 引擎下的真实构建与运行。面试近期需要一个已经验证的启动方案。

### 决策

把 Windows 本机原生启动作为当前交付基线；保留容器配置作为下一阶段部署候选。只有完成容器构建、启动、健康检查、持久化、备份恢复和回滚验证后，才宣称 Docker 部署可用。

### 结果

正面影响：

- 当前演示路径已有实际运行证据。
- 不会把“写了配置文件”误报为“部署已经通过”。

负面影响：

- 不同电脑上的 Python 和 Node 环境可能存在差异。
- 公网和容器上线仍需额外工作。

中性影响：

- 本机服务只用于审核和面试演示，不等于公网发布。

### 备选方案

- 立即以 Docker 为唯一方案：环境一致性更强，但当前无法验证。
- 直接部署云平台：可分享链接，但涉及账号、费用、安全和发布授权。

### 重新评估条件

在具备 Docker 环境或确定云平台后，执行完整部署验收并新增部署 ADR。
