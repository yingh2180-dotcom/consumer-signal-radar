MVP 是“最小可用版本”：保留一条真正跑通、可解释、可追溯的流程，先不增加全天云端计算、复杂账号体系和自动消息推送。高质量体现在数据口径、交互、证据和异常处理，不靠堆功能。

本轮生成的是方案文档。没有修改旧应用、数据库、凭据、正式架构决策或网页配置，也没有公开发布。

## 2. 原方案与本版有什么不同

| 项目 | 原最终方案 | 本版 Demo MVP 推荐实现 |
|---|---|---|
| 目标 | 珀莱雅真实采样研究与工程验证 | 求职展示，证明流程与产品设计 |

| 公开数据使用 | 导入公开中文美妆评论及独立标签 | 当前只参考公开数据分类；未下载或再分发原文，许可尚未核实 |
| 产品对象 | 固定三款珀莱雅产品 | 当前数据为演示产品 A/B/C，不伪造真实产品绑定 |
| 业务结论 | 对合格业务样本形成有证据的洞察 | 展示“演示样本中的模式”，不声称珀莱雅真实痛点 |
| 清洗与标注 | Cleaner、Reviewer、Tagging、Audit 模型角色 | 推荐先提供明确标识的规则演示；真实模型路径取得配置与费用授权后验证 |
| 聚类 | 中文 Embedding + KMeans 发现标签盲区 | 第一轮先不安装大模型或训练聚类；后续单独验证，未启用时明确显示状态 |
| 评测 | 独立人工 Gold 与 Benchmark 分开评测 | 合成期望结果只测工程行为；无人工 Gold 时 F1 显示“尚未评测” |
| 趋势 | 满足两月窗口、样本门槛、连续三窗才生成 | 当前无真实发布时间，显示“无法计算趋势”，不伪造日期和增长 |
| 存储 | 分层 CSV/JSON 与冻结文件 | Supabase 保存结构化记录和私有文件；保留本机分层产物便于复现 |
| 网页 | 业务 Dashboard + Model Ops Dashboard | 保留业务演示、流程、证据、质量四个明确入口 |
| 消息推送 | 飞书 Alert、周报、新主题提醒 | 首版不外发，不把未连接的功能画成已经成功 |
| 托管 | 文档未明确平台 | 网页托管到公网；分析先本机运行；托管账号与平台另行确认 |

### 2.1 保留的关键原则

- 原文不覆盖；每次加工保存新结果，同一个 `record_id` 全流程不变。
- 一条评论可以包含多个观点；按不同 `record_id` 统计，不按标签行数重复计数。
- 结论可以回到指标、特征和原文；重要结论尽量绑定 3–5 条不同记录，不足时显示警告。
- 代码计算指标，模型只判断语义和生成有证据的建议，不让模型编造数字。
- 测试数据与真实业务数据隔离；样本不足、未执行和计算为零必须分开表示。
- 版本、运行记录和快照可追溯；不能用新运行悄悄覆盖旧结果。

### 2.2 与旧版项目的关系

现有 `production/` 已有 React/Vite、FastAPI、SQLite、worker、证据和报告基础。旧版的七天趋势、综合机会评分、重新生成评论编号等行为不符合本次方案，不能直接继承。

旧架构文档还规定本机同源部署和 SQLite；2.0 最初在独立目录中完成审核，GitHub 版本迁移到 `codex/v2-rebuild` 的仓库根目录。1.0 通过 `v1.0.0` 与 `release/1.x` 保留。ADR 指“架构决策记录”，用于解释技术选择及其边界。

## 3. 一页项目地图与整体架构

| 维度 | 当前状态与目标 |
|---|---|
| 用户 | 招聘方主要浏览作品；你本人运行分析、审核和发布 |
| 现状 | 已有旧网页与处理系统；已准备 1000 条合成输入及独立测试期望 |
| 问题 | 旧指标与新方案冲突；新方案尚无可直接使用的完整标签体系；尚未连接 Supabase |
| 优化后结构 | 展示、存储、处理分工明确；测试数据只在演示空间展示 |
| 首版范围 | 导入 → 清洗 → 结构化观点 → 指标/证据 → 快照 → 可交互网页 |
| 完成标准 | 电脑实际打开、流程能跑、证据可查、指标可复算；公网发布后另测匿名访问 |

```text
你的电脑：本机工作台
  导入合成 CSV → 启动 Python 处理 → 核对错误与待审核记录
                                      ↓
                         分层结果 + 运行记录 + 冻结快照
                                      ↓
Supabase：云端保存
  私有原始文件 / 各层结果 / 证据关系 / 审核记录 / 已批准公开快照
                                      ↓
公网网页：招聘方访问
  样本洞察 → 五层流程 → 原文证据 → 数据质量与作品说明
```

“快照”是一份固定版本的分析结果：展示时读取这份结果，不临时重跑分析。电脑关机后可以继续看已发布结果；此时不能启动新的本机分析。

Supabase 是数据和权限平台，不会自动理解评论。其 PostgreSQL 数据库适合保存结构化结果，Storage 适合保存原始文件，Queues 可管理后台任务。[官方数据库说明](https://supabase.com/docs/guides/database/overview)、[文件存储说明](https://supabase.com/docs/guides/storage)、[任务队列说明](https://supabase.com/docs/guides/queues)。

首版由本机显式启动处理，不引入云端任务队列、定时任务或第二套长驻后端。Supabase Edge Functions 可处理短任务，但有内存、CPU 和运行时长限制；不把本方案的整批 Python 分析和中文模型安装塞入云端函数。[官方限制](https://supabase.com/docs/guides/functions/limits)。

## 4. 前端呈现什么

前端是用户看见并操作的网页。推荐以浅色分析工作台为设计方向，强调清晰、易读和可信；具体配色、布局属于后续待审核设计，不在本文中宣称已确认。

按第一性原理，公开页面先证明三件事：结果是否有用、结论是否能追溯、方法边界是否诚实。因此信息优先级固定为“总览与洞察 → 证据 → 方法与质量”。五层流程用于增强可信度，不作为抢占首屏的主叙事；运行按钮、人工复核、同步和发布属于内部管理入口。

顶部持续显示“合成样本 · 流程演示”、演示产品、运行模式、快照日期和更新时间。招聘方不必注册就能浏览批准公开的演示内容；管理功能不会对匿名访客开放。

### 4.1 页面一：样本洞察

保留原方案五个区域，但所有数字只描述合成样本。

| 区域 | 展示内容 | 可操作内容 |
|---|---|---|
| 总览 | 原始条数、有效条数、待审核条数、最新快照 | 产品筛选、点击数量查看对应记录 |
| 痛点与优点 | 各主题不同评论数、提及率、样本量 n、支持状态 | 点主题进入证据；分别查看正向与负向观点 |
| 产品与主题对比 | A/B/C × 标签的热力图与样本量 | 点单元格查看指标定义及证据 |
| 肤质与场景 | 原文明示的肤质或场景，缺失单独列出 | 筛选切片；少样本显示提示 |
| 研究候选 | 事实、模式、待验证假设、建议、验证动作 | 展开原文；没有足够证据时仅显示候选提示 |

不出现综合机会分、主观严重度排名、市场占比或因果断言。第一版以主题提及数量和明确的分母展示，不引入尚未确认的“高频”阈值。趋势位置显示当前缺少发布时间、无法计算；不绘制装饰性增长线。

### 4.2 页面二：五层流程

用一条从左到右的流程图或移动端纵向流程展示 L1–L5。每层有输入数量、输出数量、耗时、处理方式、成功/失败/待审核状态和产物入口。

点击 L2 看保留、过滤和冲突明细；点击 L3 看一条评论的多个观点、证据片段与校验；点击 L4 看指标口径；点击 L5 看本次快照。界面区分“规则演示”“真实模型处理”“未执行”，不把离线规则写成 Agent 已调用成功。

### 4.3 页面三：证据浏览

- 记录列表：编号、演示产品、原始文本、处理状态；支持搜索和分页。
- 点击记录打开详情：原文 → 清洗文本 → 特征列表 → 指标关联 → 版本。
- 从洞察卡进入时，高亮相关原文片段；不显示不存在的平台链接。
- 一条评论多观点可逐条展开，避免用整条评论的情绪覆盖每个具体观点。

### 4.4 页面四：质量与作品说明

公开部分显示：清洗数量解释、结构校验结果、支持不足提示、版本、哪些步骤实际执行、哪些尚未启用，以及数据与作品局限。

F1 表示模型预测与独立标准答案的吻合程度。当前没有独立人工 Gold，因此显示“尚未评测”；合成测试的通过率不放进模型 F1 栏。规则处理覆盖率不叫模型准确率。

真实模型启用后，建议按正面、负面、混合、未知等类别检查，不只展示一个汇总数。后台日志和密钥不会公开；匿名访客只能看到经过整理的质量摘要。

## 5. 后台呈现什么、实际做什么

“后台”有两个含义：你本人看到的管理入口，以及用户看不见的处理程序。本版分别设计，避免将一个好看的进度条当作后台已经运行。

### 5.1 本机管理入口

管理入口与公开洞察台在信息架构上分开。普通访客不看到运行按钮、数据库表、密钥、内部异常详情或工程日志；管理入口只在本机后端健康检查通过时开放操作。

| 操作区 | 你看到什么 | 程序做什么 |
|---|---|---|
| 数据导入 | 文件预览、记录数、来源声明、错误明细 | 校验编号与演示标记，保存不可覆盖的输入版本 |
| 运行分析 | 数据版本、模式、开始按钮、进度与异常 | 建立 run_id，逐层处理，记录输出和版本 |
| 人工审核 | 原文、规则/模型判断、分歧原因 | 保存保留/过滤/标签修订及时间，生成新结果版本 |
| 结果发布 | 快照摘要、准备公开的字段、验证结果 | 审核后同步获准公开快照；不自动公开所有原始数据 |

首版不开放访客上传和任意模型调用。模型配置在本机管理环境完成，不能把密钥填进公网网页或写进前端构建产物。

### 5.2 五层处理行为

| 层 | 输入 | 输出及边界 |
|---|---|---|
| L1 | 合成 CSV | 原始记录、文件摘要、导入报告；空白记录先存档再标记，不在导入时悄悄丢失 |
| L2 | 原始记录 | clean_text、保留/过滤/待审核/错误状态及原因；同文记录标记关联，不因文本相同自动删除 |
| L3 | 合格清洗结果 | 多观点长表、固定标签、原文证据、校验与待审核队列；不能抽取观点时保留处理状态而非丢记录 |
| L4 | 合格特征与清洗记录 | 不同 record_id 计数、样本量、提及率、证据关系；未通过审核的数据不进入正式快照指标 |
| L5 | L4 冻结结果与 QA | 页面数据、可追溯快照与质量摘要；只展示 L4 数据，不在浏览器重算一套指标 |

规则模式能证明导入、结构、统计和证据的工程流程，但不能证明真实 AI 语义能力。真实模型模式应按原方案保留 Cleaner、Reviewer、Tagging、Audit 的角色边界，先小批验证、再全量；失败必须留队列，不能静默切成规则结果。

用户选择人工审核并改变记录状态后，生成新运行或新快照，不修改已经公开的历史结果。没有模型导致语义步骤未执行时，状态应为“规则演示/未执行”，不伪造零冲突或全量审核通过。

## 6. 数据、血缘与公开接口

### 6.1 Supabase 保存什么

以下为推荐逻辑结构，正式建表前需做 SQL 草稿与权限审核，不直接修改现有数据库。

| 数据组 | 推荐表或文件 | 核心关系 |
|---|---|---|
| 项目与来源 | projects、datasets、raw_records | dataset_id + record_id；保存 source_origin、角色和合成标记 |
| 清洗 | cleaning_results、review_actions | run_id + record_id；保存状态、理由和人工审核历史 |
| 特征 | features、feature_checks | feature_id → record_id；保留标签、片段及校验状态 |
| 决策 | decisions、evidence_bindings | decision_id → feature_id → record_id；指标与证据分开 |
| 运行与快照 | pipeline_runs、snapshots | 绑定数据、Schema、清洗、Prompt、Model、Metric 版本 |
| 质量 | qa_reports | run_id → 各层检查；未执行与零错误区别存储 |
| 公开内容 | published_demo_snapshots | 只保存审核过的展示数据，不开放私有底表 |
| 私有文件 | Storage 中分开的 Raw、reference、产物目录 | 原文与期望答案物理分离；上传禁止覆盖旧 Raw |

Raw 不可覆盖要靠实际数据库权限与文件写入约束实现，不能只在 README 写一句“只读”。需要在测试中证明普通应用身份无法更新/删除 Raw，也无法覆盖旧文件；后台高权限维护仍必须受控，不承诺管理员无法破坏数据。

### 6.2 测试数据为什么也能演示图表

`business` 和 `demo` 是两套明确的展示/统计上下文，不是把测试角色换成业务角色。

- 业务上下文仍只允许合格 `business_core`；当前其样本量为 0，不能产生珀莱雅业务排行。
- 演示上下文只接受本批明确的 `synthetic_demo`；展示“合成样本提及率”，不声称真实消费者比例。
- 当前所有记录的 dataset_role 仍为 pipeline_test。仪表盘与接口持续传递 context=demo 和来源标记。
- 未来公开 Benchmark 也属于测试角色，但不能混进本批合成样本的分母；按独立 dataset_id 展示和评测。
- 当前样本没有平台与采样层，不得补成天猫、小红书或 natural_base。演示扩展字段不冒充原方案平台采集 Schema。

最少指标定义：某产品当前合格清洗记录的不同 record_id 数为分母；提及某标签的不同 record_id 数为分子。一条评论对同主题多次表达只计一次；同一评论可以同时进入正向与负向提及，因此两者不强行相加为 100%。展示分子、分母与筛选条件。

对产品、标签、肤质/场景等已支持筛选，由处理程序或数据库生成匹配口径的指标结果；前端选择对应结果，不用证据列表长度临时计算提及率。未支持任意组合时，明确限制筛选，不提供看似可用但改变不了口径的控件。

### 6.3 最小输入输出契约

| 操作 | 输入 | 输出 |
|---|---|---|
| 导入 | CSV、dataset_id、演示来源声明 | 导入报告、稳定 record_id 集、Raw 文件摘要 |
| 执行 | dataset_id、处理模式、版本配置 | run_id、分层产物、QA 和错误明细 |
| 冻结 | 合格 run_id | snapshot_id、不可变指标、证据和展示数据 |
| 公开查询 | published snapshot_id、已支持筛选 | context=demo、来源说明、指标、样本量、证据及支持状态 |
| 查看证据 | snapshot_id + decision_id/record_id | 对应记录和特征；跨快照或未获准记录不可读取 |

不在方案稿中假定新增一整套 REST 服务。现有本机入口可调用 Python 处理模块，公网网页通过 Supabase 读取发布数据；接口形式在确认复用路径后落实，逻辑输入输出必须遵守上表。

### 6.4 权限与发布

- 原始文件、Gold/测试期望、运行明细和审核操作默认私有；匿名访客仅可读公开快照。
- RLS 是“按访问身份限制可见记录”的数据库规则；不能只在网页隐藏管理按钮。
- 前端使用可公开的 publishable key；service_role/secret key 和模型凭据只在受控服务端或本机环境使用。
- 如果使用公开视图，需要校验其是否绕过底表权限；优先独立发布表/内容，不暴露完整私有库。
- 匿名写入、越权读私有 Raw、读取独立答案等必须实测拒绝。
- Supabase 和网页托管是两件事。最终托管平台、账号、区域、费用及公开对象还没有确定，不承诺免费或国内访问速度。

## 7. 整体如何执行

### 7.1 行动路线图

| 阶段 | 行动与交付 | 依赖 | 验证/确认点 |
|---|---|---|---|
| 0 · 确认 MVP | 审核本文，锁定独立目录、规则起步、真实模型后接的范围 | 用户对策略的确认 | 不覆盖旧版；不把方案稿写成正式 ADR |
| 1 · 本机纵向流程 | 接入 1000 条合成输入；完成 L1–L5 分层数据与快照 | 明确演示标签表；本机依赖 | 编号与数量可解释；可抽查完整证据链；无业务数据混入 |
| 2 · 可交互网页 | 完成四个页面与五区域洞察；接本机快照 | 阶段 1 的数据契约 | 实际点击筛选、证据、流程明细；桌面/手机布局可用 |
| 3 · Supabase | 生成建表和权限草稿；连接确认的项目，保存五层产物 | 用户账号授权、指定项目、云端上传范围 | 私有读写权限、匿名只读发布内容、Raw 覆盖拒绝 |
| 4 · 公网展示 | 构建并发布经过审核的合成样本快照 | 托管平台、账号和发布确认 | 当次打开实际网址；匿名浏览正常；无密钥与私有数据 |
| 5 · 模型增强 | 可选：小批真实模型 → 校验 → 1000 条处理 → 新快照 | 模型配置、发送同意与费用上限 | 请求确实执行、错误有记录、证据有效；不冒充已完成 F1 |

最快跑通顺序是先用本机产物串起网页，再接云端持久化与公网发布。云端最终仍保存完整流程数据；本机先跑是解除账号配置依赖，不是把 Supabase 从方案中取消。

### 7.2 合理使用子 agent

主 agent 负责数据契约、演示隔离、最终集成和验收。契约锁定后，可以同时安排三个独立任务：前端交互、Python 流程、Supabase 数据与权限草稿。

各自负责不同目录；修改共享契约必须先回报主 agent。集成后再安排独立审核检查统计口径和安全边界。不能让多个 agent 同时修改核心 Schema 或同一页面，也不能因为并行而放弃端到端验收。

### 7.3 每阶段交付方式

- 必要依赖已有则复用；新安装先核实来源与目录权限，不为了追求完整安装无关 Skills 或服务。
- 网页修改前建立真实可回退检查点；完成后实际验证电脑链接，再交付“待审核版本”卡。
- 当前没有修改网页，所以本轮不启动预览服务、不把历史本机网址说成可用。
- 连续调整相对同一个已认可基线；撤回只影响本次范围，不影响旧应用和已认可内容。
- 登录、付费、外发、上传到新云端项目、公开发布或改变正式目标时，说明具体对象和影响后找用户确认；普通范围内实施不重复设确认关卡。
- 不承诺未经验证的小时数。先交付实际可访问版本，用验证结果报告进度。

## 8. 验收怎么判断

| 检查 | 通过标准 |
|---|---|
| 输入一致性 | 1000 条 Raw 存档、1000 个唯一 record_id；没有隐性重编号 |
| 数量解释 | 原始数 = 保留 + 过滤 + 待审核 + 错误；各状态互斥且可查明细 |
| 同文处理 | 20 个已知同文测试可追溯；不直接用全文去重消除不同记录 |
| 标签与证据 | 特征编号唯一；证据是对应文本真实子串；多观点保留；非法标签进入错误队列 |
| 统计 | 独立复算不同 record_id 与分母；加入额外标签行不增加评论提及计数 |
| 隔离 | 业务样本仍为 0；演示接口明确 context=demo；Benchmark 不混入合成数据分母 |
| 真实状态 | 未执行 AI/聚类明确标记；没有真实日期时无趋势；没有人工 Gold 时无 F1 达标声称 |
| 深入查看 | 抽查 5 个支持足够的结论，从 decision_id 找到 feature_id、record_id 和 Raw；少证据时显示警告 |
| 筛选 | 更换产品或切片后指标与 n、证据一致；没有结果显示空状态，不残留上一筛选数据 |
| 快照 | 相同数据与固定配置产生一致指标；新运行不覆盖旧快照；版本元数据齐全 |
| 权限 | 匿名可读公开演示快照；不可写入、不可读私有 Raw/答案/审核日志；前端无密钥 |
| 访问 | 电脑实际访问和交互验证；公网部署另测最终网址；同 Wi-Fi 手机链接仅在实际可用时提供 |

本轮已验证的仅是生成样本：保存的 CSV 为 1000 行、编号唯一、全部 pipeline_test、输入与期望独立、文件摘要匹配。以上应用级验收还未执行，不能用数据检查替代。

## 9. 已确定、推荐但需确认、需要提供

### 9.1 已确定

- 求职初版 Demo MVP，质量优先，同时尽快跑起来。
- 用户没有真实评论；授权寻找公开美妆数据，使用合成样本证明流程。
- 可合理使用子 agent 与适合项目的 Skills；不无意义并行。
- 当前已有 1000 条独立合成输入，真实品牌、平台、日期和金标不可凭空补齐。

### 9.2 实施前需要确认的策略包

**2.0 已按以下裁剪实施：独立版本目录、四页面、规则演示先跑、模型后接、无数据则不做趋势/F1、首版不做飞书与云端队列。**

标签体系也需确认：建议先用公开参照的 13 类作为演示基础类别，另列完整子标签、UNKNOWN/OTHER 和证据规则供审核，不擅自把它认定为原文档正式 schema_v1。两个模式一旦启用，应共用同一已确认演示 Schema。

本版不开启趋势、自动机会阈值和新主题提醒，因此原方案未定义的变化阈值、窗口锚点和提醒规则不阻塞首版；启用这些能力时再明确确认，不暗中创造阈值。

### 9.3 云端实施需要的信息与权限

| 项目 | 当前状态 | 需要的最少输入 |
|---|---|---|
| Supabase | 当前可读 Skill 与官方文档，但未发现可调用的 Supabase 项目工具 | 指定已有项目或同意新建；项目 URL；由本人完成登录/授权，不把 secret key 发到聊天 |
| 网页托管 | 尚未选定和授权 | 平台与账号；发布对象和可公开的数据范围；先核实实际访问条件与套餐 |
| 真实模型 | 本轮尚未验证或获得新费用策略 | 服务商、模型、累计预算及数据发送同意；凭据在受控环境配置 |
| 设计 | 当前仅推荐方向 | 审核页面草图；重大布局或展示策略不自行锁定 |

当前文档生成和样本准备可全自动；云端账号登录与项目授权需要用户本人完成。插件 Skill 的存在不等于项目已连接，不能宣称已经建表或上传成功。

完成本文审核后，以确认的 MVP 策略为依据开始纵向流程与网页设计；Supabase 和托管需要的账号步骤在具体目标与草稿准备好后完成。本文新增在现有项目文档区，不替代原最终方案或既有正式决策。
