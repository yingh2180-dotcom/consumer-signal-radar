## 四 已完成工作

### 4.1 版本归档

2.0 已形成独立正式目录和压缩交付包。目录内包含前端、后端、数据、Supabase、整体方案、设计稿、验收截图、运行产物和启动入口。压缩包已做 CRC 完整性检查，没有损坏文件，也没有包含 `node_modules`、Python 缓存或本机运行日志。

### 4.2 合成演示数据

已生成 1000 条原创合成美妆评论，包含演示产品、肤质、场景和多观点句式。所有记录固定标记为 `synthetic_demo` 与 `pipeline_test`，没有伪造真实平台、真实发布时间、真实产品编号或来源链接。

数据中有计划地放入空白、模板文本、重复文本和混合观点，用于证明清洗、留痕、多观点抽取和证据绑定是否有效。独立期望文件没有被处理流程读取，因此不会形成答案泄漏。

### 4.3 五层处理后端

| 层级 | 已执行行为 | 当前结果 |
|---|---|---|
| L1 | 校验数据身份、编号、数量和原始文件哈希 | 1000 条 Raw 完整入库准备 |
| L2 | 清洗空白与模板文本，记录保留、过滤和重复关系 | KEEP 960，FILTER 40 |
| L3 | 用 13 类原创固定规则抽取一条评论中的多个观点 | 980 条观点特征 |
| L4 | 按不同 record_id 去重统计，绑定证据并生成研究候选 | 140 个预计算切片，1840 条分群决策 |
| L5 | 组装网页快照，执行 Schema、证据与数量检查 | 1 个可追溯 2.0 快照 |

每次运行会建立新的 `run_id` 和独立目录，旧运行不会被覆盖。人工 KEEP 或 FILTER 复核采用追加记录，重新运行后才进入新快照。

### 4.4 前端网页

前端按照第一性原理重新组织为四个页面。

1. **总览与洞察**先展示样本范围、主要问题线索、正向反馈和研究候选，并支持产品、肤质、场景筛选。
2. **证据追溯**把指标连接到观点编号、评论编号和高亮原文，证明页面数字有来源。
3. **方法与边界**展示五层实际输入输出、质量检查和未启用能力，避免把规则演示包装成 AI 模型结果。
4. **内部运行台**提供本机重跑、历史状态和人工复核；静态公开页面不会出现可写操作。

页面持续显示合成样本、规则模式和真实业务样本为 0。数据库表、Secret 密钥、内部异常详情和工程日志不会暴露给普通访客。

已完成 Supabase 五层数据结构草案、权限检查脚本和默认离线的同步适配器。适配器可以把当前快照映射为 1 个数据集、1 次运行、1000 条 Raw、1000 条清洗结果、980 条特征、980 条特征检查、1840 条分群决策、5033 条证据绑定、1 份 QA 和 1 个快照。

## 五 前端与后端的职责边界

### 5.1 前端呈现

前端负责帮助观看者理解结果和检查可信度。它呈现样本范围、切片筛选、主题提及数量、提及率、支持状态、研究候选、五层状态和原文证据。前端只读取后端预计算的 140 个切片，不在浏览器里重新计算业务指标。

### 5.2 内部运行台呈现

内部运行台负责本机操作和过程控制。它呈现运行编号、模式、时间、状态、当前快照、人工复核动作和 Supabase 同步状态。它不会把数据库结构、密钥或完整内部日志作为普通产品界面展示。

### 5.3 后端处理

后端负责数据校验、清洗、观点抽取、指标计算、证据关系、质量检查、历史运行和快照生成。Supabase 负责未来的五层过程数据保存、权限隔离和审核后公开快照，不负责自动理解评论内容。

## 六 尚未完成事项

### 6.1 Supabase 云端连接

尚未指定或授权 Supabase 项目，因此 SQL 没有在真实 Postgres 中执行，云端权限检查和实际同步也没有发生。需要用户提供项目名称或 Project URL，并在本机完成账号登录或授权。Secret Key 不应粘贴到聊天中。

### 6.2 公网部署

当前链接是电脑本机审核地址，不是互联网地址。公网发布需要确定托管平台、公开或私有访问范围，以及内部运行台是否继续只保留在本机。推荐公开页面只读，内部运行与复核保持本机或登录保护。

### 6.3 真实 AI 与评测

当前采用固定规则演示，没有调用大模型。没有独立人工 Gold，因此不能显示 F1 或模型准确率。要启用真实 AI，需要先明确模型、费用上限、隐私边界和评测集，再在离线评测达标后替换规则抽取器。

### 6.4 真实业务数据

当前没有真实评论。真实数据接入前需要确认合法来源、授权范围、字段、脱敏方法、保存周期和删除机制。合成数据与真实数据必须使用不同的 dataset role 和发布流程。

## 七 后续执行计划

### 阶段一 本地 2.0 审核

**目标**：确认页面信息架构、视觉和文案符合求职作品展示需求。

**步骤**：

1. 打开本机审核地址，依次浏览四个页面。
2. 用产品、肤质和场景筛选检查切片变化。
3. 从一个问题指标进入原文证据，核对高亮片段。
4. 查看方法与边界页，确认未启用能力表达清楚。
5. 查看内部运行台，确认管理功能与公开洞察分开。
6. 使用“通过本次审核”或“继续调整：具体内容”给出反馈。

**完成标准**：页面结构和文案获得用户认可，2.0 成为新的已认可基线。

### 阶段二 连接 Supabase 五层存储

**目标**：把本地已验证的五层过程数据安全写入指定 Supabase 项目。

**依赖**：用户指定 Supabase 项目并授权建表与写入。

**步骤**：

1. 核对项目地址、环境和用途，确认是演示项目。
2. 在 SQL Editor 审阅并运行 `supabase/schema_preview.sql`。
3. 配置 `demo_private` 为 Data API 的 exposed schema，但只给 `service_role` 私有表权限。
4. 运行 `supabase/permission_checks.sql`，检查匿名用户、登录用户、Raw、Gold 和 Storage 权限。
5. 在本机后端设置 `SUPABASE_URL` 和 `SUPABASE_SECRET_KEY`。
6. 再次执行 dry-run，确认数据数量和哈希没有变化。
7. 使用明确的项目 URL 执行私有五层同步。
8. 读取云端行数、随机证据关系和权限结果，形成云端验收记录。

**完成标准**：五层数据完整写入；匿名身份不能读私有 Raw 和 Gold；旧 Raw 与旧快照不能被普通应用权限覆盖。

### 阶段三 发布只读演示网页

**目标**：提供招聘方可打开的只读演示链接。

**依赖**：用户确认托管平台和访问范围。

**步骤**：

1. 只发布审核通过的合成快照，不公开私有过程表。
2. 前端配置公开快照读取地址，移除所有本机管理操作。
3. 保持合成数据、规则模式和业务样本为 0 的显著标识。
4. 部署后检查桌面、手机、刷新、证据跳转和错误页面。
5. 检查前端构建物中不存在 Secret Key、模型密钥或内部路径。
6. 输出公开链接、版本号、快照编号和回退方式。

**完成标准**：公开链接可访问，页面只读，证据可追溯，私有数据和写接口不可访问。

### 阶段四 接入真实 AI 并建立评测

**目标**：用可评测的 AI 抽取器替换或增强固定规则。

**依赖**：模型选择、费用上限、隐私规则和人工标注资源。

**步骤**：

1. 冻结标签 Schema 和证据字段。
2. 建立独立人工 Gold 集，禁止作为提示词示例或处理输入。
3. 记录 prompt version、model identifier、temperature 和运行批次。
4. 对类别、情绪、证据片段分别评测，并报告每类样本量。
5. 设置上线阈值、待审核条件和失败回退规则。
6. 只有达到阈值后，才让 AI 输出进入正式演示快照。

**完成标准**：评测可重复、无答案泄漏、指标可解释、低置信结果进入人工审核。

### 阶段五 接入真实业务数据

**目标**：从流程演示升级为真实消费者洞察项目。

**依赖**：合法数据来源、业务口径和隐私治理。

**步骤**：

1. 建立真实数据采集说明和授权记录。
2. 将真实数据与合成测试数据物理和逻辑隔离。
3. 运行小批量试处理并人工抽检。
4. 重新定义真实业务的主题、支持阈值和研究问题。
5. 对正式快照执行审批，再允许业务页面读取。

**完成标准**：来源合法、数据可删除、指标口径确认、业务结论经过人工审核。


### 9.4 本地修改执行循环

如果用户要求调整页面、规则或接口，AI 必须按以下循环执行：

1. 明确修改属于前端、后端、数据契约还是 Supabase。
2. 修改前确认分支和回退范围，只改 2.0 当前工作分支中的相关文件。
3. 先增加或更新能证明预期行为的测试。
4. 完成最小范围修改。
5. 重新运行受影响模块测试，再运行端到端验收。
6. 前端变更必须重新构建，并用真实浏览器检查电脑与手机尺寸。
7. Pipeline 或版本字段变更必须生成新 run_id、更新当前快照并重新执行 Supabase dry-run。
8. 更新 `RELEASE_NOTES.md`、本文档和验收截图。
9. 重新生成压缩包并验证 CRC、文件清单和 SHA-256。

### 9.5 Supabase 执行状态机

Supabase 云端操作必须逐步过闸，任何一步失败都应停止，不得跳过检查。

| 状态 | 前置条件 | AI 动作 | 验收证据 | 下一状态 |
|---|---|---|---|---|
| S0 本地准备完成 | 当前测试通过 | 读取 schema、权限脚本和 dry-run | 本地计数与哈希一致 | S1 |
| S1 项目已确认 | 用户指定 Project URL | 核对项目和环境，不读取其他项目 | 目标项目记录 | S2 |
| S2 建表已授权 | 用户授权建表 | 执行 schema_preview.sql | 表、约束、RLS 和桶存在 | S3 |
| S3 权限已验证 | Schema 成功 | 执行 permission_checks.sql | 事务回滚且检查无异常 | S4 |
| S4 私有同步已授权 | 本机 Secret 已配置 | 先 dry-run，再 execute | 五层行数、文件哈希和随机证据一致 | S5 |
| S5 待发布审核 | 私有同步通过 | 生成待发布快照预览 | context、business_count、公开字段通过 | S6 |
| S6 公开发布已授权 | 用户明确批准该快照 | 写入 approved public copy | 匿名只读、私有表不可访问 | 完成 |

如果用户没有给出 Project URL、账号授权或发布批准，AI 必须停留在对应状态，不得自行创建项目或猜测目标。

### 9.6 公网部署执行状态机

1. 先确认托管平台、公开或私有访问、目标项目和费用边界。
2. 公开构建只保留洞察、证据和方法页面；内部运行台默认不公网开放。
3. 公开页面只读取 `approved=true` 的合成快照。
4. 部署前扫描前端构建物，确认没有 Secret、内部路径或写接口配置。
5. 部署后验证首页、筛选、证据跳转、刷新、手机布局、404 和权限拒绝。
6. 记录公开 URL、部署版本、snapshot_id、回退版本和验证时间。
7. 未经发布授权，不得把本地预览链接描述为公网部署。

### 9.7 停止并询问用户的条件

遇到以下任一情况，AI 必须停止相关操作并向用户说明影响和推荐路径：

- 需要登录、账号授权、付费、建表、写入云端或公网发布。
- 目标 Supabase 项目、托管平台或访问范围不明确。
- 需要修改 1.0 文件、删除重要文件或改变现有认可基线。
- 数据中出现真实来源、个人信息、真实产品绑定或 `business_core`。
- 测试失败、数量不守恒、证据无法回到原文或快照版本不一致。
- 需要引入新的模型、第三方服务、费用或数据发送范围。

### 9.8 每次交付必须报告

每次 AI 完成一组修改后，必须报告修改范围、测试结果、当前 snapshot_id、仍未完成项、风险、正式文件位置和可点击审核链接。网页交付必须提供待审核版本卡，并支持“通过本次审核”“撤回本次修改”“继续调整：具体内容”三个口令。

## 十 推荐的下一步

当前最短路径是先完成本地 2.0 页面审核，再连接 Supabase。这样可以先锁定用户看见的结果与数据契约，避免数据库部署完成后又因页面或字段变化返工。

本地审核通过后，建议按“Supabase 私有五层同步 → 权限验收 → 只读公开快照 → 公网页面”的顺序执行。真实 AI 和真实业务数据放在演示闭环稳定之后接入。
